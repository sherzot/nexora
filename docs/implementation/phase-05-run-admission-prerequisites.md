## Existing contract and specified use case

[I] Phases 1–4 supply the HTTP skeleton, owner IDs, partial immutable configuration/assignment attribution, pure Run lifecycle and pure versioned preparation. [P] Specify one human-initiated creation through a trusted authenticated workload/represented-authority path, in one explicitly selected tenant/project, for one pinned Instance/configuration and Task/assignment. ## Creation boundaries and disposition contract

[P] Semantic sequence: proposed creation intent → trusted source/scope resolution → current creation authorization and required review → authoritative durable Created record/disposition → separately governed queue admission → bounded Runtime execution → separately governed Tool/Execution dispatch/effects. It is not one cross-owner transaction and is not a selected Go/API/schema design.

[P] Request identity is `(Runtime creation purpose, trusted operating tenant, admitted producer namespace, stable request token)` as proposed in ADR-013. Project, pinned source revisions and represented actor/purpose are bound material intent. Transport attempt and actual retry workload are distinct evidence; a different workload cannot inherit retry rights without current validated eligibility. A changed project or material intent under the same identity conflicts.

[P] On matching accepted redelivery, return the same Run/disposition through a current-authorized read; no new creation or execution. Conflicting duplicates reject as integrity conflicts. Unknown acceptance requires same-identity reconciliation, not a new identity or a blind repeat. A lack of retained evidence is not proof of non-acceptance. Policy/source re-evaluation for proven-absent acceptance is separate from returning an existing disposition; a recorded final rejection does not silently become a new accepted request.

[P] Distinguish invalid intent, unresolved source relationship, current denial, required Approval unusable, dependency unavailable, conflicting request identity, confirmed creation and unknown creation outcome. Any scoped not-found response must preserve confidentiality; definitive absence requires the future owner's approved consistency/retention contract, not a missing cached record. Existing local preparation errors remain local errors and do not establish any of these durable dispositions.

[P] Successful future creation freezes its historical attribution and would start at Created/revision 1. A later queue denial leaves that fact intact; it does not automatically finish, delete or recreate the Run. Valid subsequent transitions remain Phase 3/4 operations under a future authoritative application boundary.

## Source changes, historical interpretation and correction

[P] Required H1 bindings cannot silently become H2. Reject a material mismatch or re-resolve/re-evaluate the original pinned intent if its meaning has not changed. A newer latest revision does not invalidate still-eligible pinned H1 by itself; owner revocation/changed relationships can. Revised material intent requires a new linked request after the prior disposition is reconciled, not mutation of an uncertain request.

[O] Source observations and policy checks must be made valid at the creation acceptance point through a reviewed protocol (O3). No atomic transaction spans source owners/Security/Approval/Runtime by assumption. The specification cannot promise zero stale-use exposure, make a pre-check atomic, or select a lease/fence implicitly.

[P] References need immutable identity and preserved historical meaning, not just a source URL or hash. Keep bounded permitted projections where necessary and lawfully retainable; minimize identity data and secrets. Later corrections append linked assertions with correction identity, authorized actor/reason and supporting evidence; do not rewrite original attribution. Wrong tenant/source attribution is restricted investigation/correction work, not an ordinary cross-tenant record move. Governed redaction/suppression records resulting interpretation gaps.

## Minimum evidence and acknowledgement

[P] Runtime must produce enough permitted evidence to relate request intent, Run, source identity/revisions/relationship checks, historical initiator/delegation/workload/scope, applicable current creation decisions/required Approval use, source-change observations, final or unknown disposition, and custody/retained obligation. Source owners produce the facts they own; Audit policy defines required custody/independence/retention; custodian records actual acknowledgement. No raw secret, private reasoning or wholesale source payload is necessary by default.

[P] Recommend owner-local durable evidence for this non-dispatching creation class only with explicit Audit/Security risk-policy approval. Where independent custody is required, its receipt is part of the confirmation gate. Atomically bind owner-created state, request-to-Run mapping and required evidence/publication intent, or prove a reviewed equivalent. Do not report confirmed creation from a constructed value, post-commit best-effort send, volatile exporter or Temporal acknowledgement.

[O] The actual custody policy, transaction protocol, historical serialization, creation-disposition lookup, absence proof, retention and restore consistency are O1/O4/O5. A response lost after possible acceptance remains Unknown until authoritative evidence resolves it. Recovery investigation itself needs current authorization. No blind consequential retry follows from any disposition or Approval.
